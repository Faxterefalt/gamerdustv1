# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Gamerdust es una app web de asistencia al diseño narrativo de videojuegos (proyectos, lore, personajes, escenas, diálogos ramificados con estado, análisis emocional, validación de coherencia, estimación de coste y colaboración por roles). Los comentarios del código están en español; mantén ese idioma. La interfaz es bilingüe (español por defecto e inglés): **nunca escribas texto visible directamente**, usa `__()` (ver "Idiomas (i18n)").

## Estructura del repositorio

- La raíz del repositorio **es la app**: Laravel 13 (PHP 8.3+) + frontend React 19 / TypeScript servido con Inertia v2, Vite 8 y Tailwind 4 (`app/`, `bootstrap/`, `config/`, `database/`, `lang/`, `public/`, `resources/`, `routes/`, `storage/`, `tests/`). Todos los comandos se ejecutan desde la raíz y el *document root* es `public/`.
- Hoy el análisis emocional lo hace PHP con Groq (o por palabras clave sin clave) detrás del contrato `EmotionAnalyzer` (ver abajo). El motor Python que se había previsto no existe; su diseño está en [docs/narrative-engine.md](docs/narrative-engine.md).
- `compose.yaml` — solo MySQL 8.4 (BD `gamerdust`). En local se usa Laragon apuntando a `public/`.
- `docs/` — documentación: `architecture/Gamerdust_Documentacion.ipynb`, [modelo-asistencia-emocional.md](docs/modelo-asistencia-emocional.md), [despliegue.md](docs/despliegue.md) (producción: HTTPS, `.env`, `optimize`, cola, logs) y [narrative-engine.md](docs/narrative-engine.md).
- `tests/` — PHPUnit (`Feature/`, `Unit/`, `Fixtures/`), JS (`js/`) y `e2e/`: pruebas de navegador sin dependencias (Node + Chrome headless por CDP; ver su [README](tests/e2e/README.md)): `run.mjs` crea una SQLite temporal con el seeder, arranca `php -S` y ejecuta los escenarios de `scenarios/` (diálogos, guion, IA, colaboración, cuenta).

## Comandos (en la raíz)

```
composer setup             # install + .env + key + migrate + npm install + build
composer dev               # serve + queue:listen + pail + vite en paralelo
php artisan serve          # o: npm run dev  (en otra terminal)
npm run build              # build de producción de Vite
php artisan test           # toda la suite (composer test limpia config antes)
php artisan gamerdust:test [--filter=...]                # la misma suite con la salida en español y APP_LOCALE=es (composer test:es)
php artisan test --filter=BranchingEditorTest            # una clase
php artisan test --filter=test_nombre_del_metodo         # un test
npm run test:js            # tests de JS con node --test (diff de versiones, auto-formato) + test:parity
npm run test:e2e [-- --skip-build --only=script,ai]  # pruebas de navegador (tests/e2e; PHP_BINARY = PHP ≥ 8.4, CHROME_PATH)
npm run test:parity        # el evaluador JS del reproductor da lo mismo que BranchingStateEvaluator (tests/Fixtures/branching-state-cases.json)
vendor/bin/pint            # formateo PHP (Laravel Pint)
npx tsc --noEmit           # chequeo de tipos TS (no hay ESLint)
php artisan gamerdust:groq-check [--model=...]          # llamada real mínima a Groq (clave, tokens, latencia)
php artisan gamerdust:ai-metrics {project?} [--output=f.csv]  # métricas de uso y valoración de la IA a CSV (OE4)
```

Variables en `.env` (valores por defecto en `config/services.php` → `groq` y `config/gamerdust.php`): `GROQ_API_KEY`, `GROQ_MODEL` (`openai/gpt-oss-120b`), `GROQ_FALLBACK_MODEL` (`openai/gpt-oss-20b`), `GROQ_TIMEOUT` (15 s), `GAMERDUST_AI_DRIVER` (`groq`|`keywords`; por defecto `groq` si hay clave), `GAMERDUST_AI_MAX_TOKENS`, `GAMERDUST_LOG_LEVEL` (`info`) y `GAMERDUST_LOG_DAYS` (30). La clave nunca sale del servidor. En local, `MAIL_MAILER=log`: el correo de recuperar contraseña (con su enlace) queda en `storage/logs/laravel.log`.

Los tests usan SQLite en memoria (`phpunit.xml`), no MySQL. `phpunit.xml` vacía `GROQ_API_KEY`, fija el motor `keywords`, desactiva el SSR de Inertia y sube el canal `gamerdust` a `emergency` (no escribe logs); `Tests\TestCase` llama a `Http::preventStrayRequests()`, así que cualquier test que use Groq debe definir la clave con `config()` y usar `Http::fake()`. No existe `.env.example`; copiar el `.env` existente.
Con `APP_LOCALE=en` en `.env` fallan los tests que esperan textos en español (p. ej. `DÍA` en el guion); ejecutar con `APP_LOCALE=es php artisan test`. En Laragon el CLI necesita PHP ≥ 8.4 (ruta `laragon/bin/php/php-8.5...`).

## Arquitectura

### Inertia: controladores → páginas
Los controladores devuelven `Inertia::render('Modulo/Pagina')`. [resolve-page.ts](resources/js/app/resolve-page.ts) traduce ese nombre a `resources/js/features/<modulo en minúsculas>/pages/<Pagina>.tsx` (p. ej. `Projects/Index` → `features/projects/pages/Index.tsx`, `Landing` → `features/landing/pages/Landing.tsx`). Una página nueva debe seguir esa ruta o falla en runtime. Cada feature tiene `pages/`, `components/` y un `<feature>.types.ts`; layouts en `resources/js/layouts/`, clases Tailwind reutilizables en `shared/lib/styles.ts`, hooks compartidos en `shared/hooks/`. `HandleInertiaRequests` comparte `auth.user`, `flash.success/error` y `projectAccess` (rol en el proyecto de la ruta, ver "Autorización").

### Idiomas (i18n)
- **La clave es el texto en inglés** y `lang/es.json` contiene la traducción al español (con sus tildes). No existe `lang/en.json`: en inglés se muestra la propia clave. Un texto nuevo = `__('English text')` + su entrada en `lang/es.json`.
- PHP: `__('Scene created.')`, con parámetros `__('The scene :title has no clear conflict.', ['title' => ...])`. Validación, auth, contraseñas y paginación van en `lang/{en,es}/*.php`; los nombres de campo en español están en `lang/es/validation.php` → `attributes` (añade ahí los campos nuevos). Los textos del correo de Laravel (recuperar contraseña) también están en `es.json`.
- React: `__()` y `choice()` de [shared/lib/i18n.ts](resources/js/shared/lib/i18n.ts), que importa `lang/*.json` con Vite (mismo catálogo que PHP). `choice(':count scene|:count scenes', n)` para plurales. Los identificadores de BD (tipos de diálogo/lore, emociones, estados, géneros, roles) se traducen con mapas de etiquetas (`projectOptions.ts`, `analysis/labels.ts`, `lore/loreOptions.ts`, `branching/layout.ts`, `ROLE_LABELS` en `collaboration/components/MembersPanel.tsx`).
- Idioma activo: `config('app.locale')` (`es`) salvo que la cookie `locale` indique otro de `config('app.supported_locales')`; lo aplica el middleware `SetLocale`. `LocaleSwitcher` enlaza a `GET /locale/{locale}` (enlace normal, no Inertia: la página se recarga y el frontend lee el idioma de `<html lang>`).
- **Idioma del proyecto ≠ idioma de la interfaz**: `projects.language` (`es`/`en`) indica en qué idioma se escribe la narrativa. Los textos que generan los servicios de análisis y se guardan en BD quedan en el idioma de la interfaz del momento en que se generaron.

### Acceso
`AuthController` (login, registro, logout) y `PasswordResetController` (HU 1): `GET|POST forgot-password` y `GET reset-password/{token}` + `POST reset-password` (nombres estándar `password.*`), con el broker `Password` de Laravel, páginas `Auth/ForgotPassword` y `Auth/ResetPassword` y marco común `features/auth/components/AuthShell`. Mensajes genéricos (nunca revela si un correo tiene cuenta) y limitador `password-reset` (5/min por IP+correo, 20/min por IP; al superarlo vuelve al formulario con aviso). El login no tiene limitador propio.

### Estudio de proyecto (sidebar)
- `ProjectLayout` detecta si la página recibe una prop `project` (con `id` y `title`): en ese caso la envuelve en el estudio (cabecera con hamburguesa + `ProjectSidebar` + ruta). Sin `project` (p. ej. Cuenta) se muestra como página simple. Las páginas nuevas de proyecto solo tienen que pasar `project` desde el controlador. Para un lector muestra la banda "Acceso de solo lectura".
- Secciones en `PROJECT_SECTIONS` (`layouts/components/ProjectSidebar.tsx`): Panel (`Projects/Show`), Biblia Narrativa, Guion, Escenas, Diálogos (ramificación), Mecánicas, Colaboración, Análisis IA, Reportes. `also` marca rutas clásicas que activan una sección (personajes/lore → Biblia; dialogues → Diálogos).
- En escritorio el sidebar se pliega (preferencia en `localStorage`); en móvil es un `<dialog>`. `bare` en `ProjectLayout` quita márgenes y título (lo usa el editor de guion).
- Lecturas combinadas en `StudioController` (biblia, análisis, colaboración, reportes, descarga Markdown, HTML de diálogos y reporte de análisis); `MechanicController`, `CommentController` y `ProjectMemberController` son CRUD Inertia.
- **Reportes**: Markdown (`reports/markdown`), PDF del guion (`script/print`, Blade), diálogos en HTML autónomo tipo Twine (`reports/dialogues`, ver ramificación) y **reporte de análisis** (`reports/analysis`, HU 57): vista Blade imprimible armada por `Reports\AnalysisReportService` con métricas emocionales por escena en lenguaje narrativo (nunca VAD), alertas rojas/ámbar, incoherencias, sugerencias, validaciones por estado y, por análisis, la versión leída (`scene_version_id`) con "Versión actual"/"Desactualizado". No llama a la IA; ejecuta las reglas de validación como el Panel.
- Análisis IA con pestañas (`AnalysisTabs`): métricas y coherencia (`/analysis`) y evolución emocional (`/analysis/evolution`, Vistas A y B con Recharts cargado con `React.lazy`; datos de `GET analysis/emotion-timeline`, `EmotionTimelineService`, solo lectura).
- Biblia Narrativa con pestañas (`features/bible/components/BibleTabs`): Esencia (`/bible`, con el encargo y los **límites de producción** en `#limits`), Personajes (`/characters`), Lugares y Reglas del mundo (`/bible/{locations|rules}`, `BibleEntryController`). Las tres fichas son catálogo + formulario en una página (`useEntryEditor`, `EntryCatalog`, `LinkRow`); `characters/create` y `/{id}/edit` solo redirigen a `?new=1` / `?character=id`. La ficha del personaje lista los nodos de diálogo donde habla, con enlace a `/branching?node=id`.
- Personajes: concept art en el disco privado `local`, servido por `projects.characters.image` tras autorizar (no hace falta `storage:link`); escenas en la pivote `character_scene` (la misma del guion). Con archivo el formulario va en multipart (POST + `_method=put`), donde una lista vacía no viaja: la ficha envía `sync_scenes` para vaciar escenas.
- Lugares y reglas son entradas de lore (`type` location/rule) con campos propios (`subtype`, `parent_id`, `statement`, `rigidity`...). El lugar de una escena es `scenes.location_id` (vincular escenas a un lugar lo cambia); lugar ↔ regla/lore en `lore_entry_links`, guardado **en ambos sentidos**; personajes en `character_lore_entry` (`role` breaks/enforces en reglas). `shared/components/LinkPicker` se comparte con Mecánicas y con el panel del nodo.

### Editor de guion
- Rutas `projects/{project}/script/*`: `index` es Inertia, el resto JSON (como ramificación) vía `shared/lib/api.ts` (`ApiError` trae `status`, `errors` y el cuerpo en `payload`). `print` es una vista Blade con formato de guion que el navegador imprime/guarda como PDF.
- Cada escena guarda sus bloques en `scenes.script` (JSON `[{id, kind, text}]`, tipos en `ScriptService::KINDS`), `act`, `location_id` (entrada de lore) y personajes en la pivote `character_scene`. El código visible (E01…) se calcula por `order`, no se guarda.
- **Concurrencia**: el cliente reenvía `updated_at` y `version_id` (id de la última `SceneVersion`; segundo testigo porque `updated_at` solo tiene segundos). Si alguno no coincide, el servidor responde 409 con `conflict.scene` (la versión guardada) y `conflict.saved_by`, y no pisa. `ConflictDialog` ofrece Ver cambios del otro (diff), Sobrescribir (reenvía los testigos del otro) o Copiar mi versión (portapapeles + carga la guardada; Deshacer recupera la propia). Cada guardado o restauración crea una `SceneVersion` (se conservan 30 por escena).
- El cliente guarda borradores por escena con deshacer/rehacer local y solo persiste en el servidor al pulsar Guardar (Ctrl/⌘+S); `useUnsaved` avisa antes de salir. **Autoguardado local** (HU 24): cada borrador con cambios se copia a `localStorage` (`lib/localDrafts.ts`, clave por usuario y escena, debounce 700 ms y `pagehide`); al reabrir se ofrece Recuperar/Descartar si es más reciente que lo guardado. El indicador distingue guardado, sin guardar y error (nunca dice "guardado" si el servidor falló).
- Versiones: vista previa, restaurar y **comparar** por bloques (`lib/diffBlocks.ts`, LCS por id: añadido/eliminado/modificado/movido; `VersionDiff`). **Auto-formato** (`lib/scriptFormat.ts`): Enter al final de un bloque crea el siguiente según `NEXT_KIND` y una línea en MAYÚSCULAS con el nombre de un personaje de la escena pasa a `character`; todo entra en deshacer/rehacer.
- Los comentarios recargan solo la prop `comments` para no perder borradores.
- IA en el editor (JSON): `GET|POST script/scenes/{scene}/analysis|analyze` (`SceneEmotionController`, panel `EmotionPanel`; exige escena guardada: analiza la versión guardada) y `POST script/scenes/{scene}/refine` (`AiAssistController`, `RefineDialog`). "Usar como base" en una sugerencia abre `RefineDialog` con la sugerencia como instrucción y un selector de bloque. Borrador de personaje: `POST ai/character-draft`; votos: `POST ai/feedback`.

### Autorización por proyecto y colaboración
Todo cuelga de `Project`; todas las tablas de dominio tienen `project_id` con `cascadeOnDelete`. **Roles** (HU 5): el dueño (`projects.user_id`) es administrador implícito, sin fila; el resto en `project_members` (`role` admin|editor|viewer, único por proyecto+usuario, `favorite` personal, `invited_by`). `Project::roleFor($user)` devuelve `owner`|admin|editor|viewer|null (memoizado por petición) y `Project::accessibleBy($user)` lista propios y compartidos. `ProjectPolicy`: `view` = cualquier miembro (lectura, exportaciones, reportes), `update` = owner/admin/editor (**toda** escritura, incluida la IA, los votos, los comentarios y los bloqueos), `manage` = owner/admin (miembros), `delete` = solo el dueño. Los comentarios los borra su autor o un administrador; el favorito es por usuario (`projects.favorite` para el dueño, `project_members.favorite` para el resto).
- Las rutas anidadas (`projects.lore`, `projects.characters`, ...) deben además verificar que el hijo pertenece al proyecto (`abort_unless(... project_id === $project->id, 404)`); ver `ensureNode/ensureOption` en `BranchingGraphController` y `BranchingRequest::authorize()`.
- **Toda ruta nueva que escriba debe pedir `update`** (en el controlador o en su FormRequest): `CollaborationTest::test_un_lector_recibe_403_en_todas_las_rutas_de_escritura` recorre todas las rutas no-GET de `projects/{project}/*` como lector y falla si alguna no da 403 (si añades un parámetro de ruta nuevo, dale un valor en `routeParameters()`).
- En el frontend, `shared/hooks/useProjectAccess` lee `projectAccess` (`role`, `can_update`, `can_manage`, `is_owner`) para ocultar acciones; la autorización real siempre es la policy.
- Colaboración (`StudioController@collaboration` + `MembersPanel`): `POST|PUT|DELETE projects/{project}/members[/{member}]` para invitar por correo a un usuario existente, cambiar el rol y retirar (o salir uno mismo). Al retirarlo pierde el acceso en la siguiente petición y se borran sus bloqueos.
- **Edición simultánea** (HU 26, bloqueo blando sin dependencias): `edit_locks` (escena o nodo, `user_id`, `expires_at`, único por elemento). `POST locks` (latido: toma, renueva o devuelve quién lo tiene) y `POST locks/release` (`keepalive` al cerrar), con `EditLockService`; tiempos en `config/gamerdust.php` → `collaboration` (latido 20 s, caduca a 60 s). `shared/hooks/useEditLock` muestra ":name está editando..." en el guion y en el panel del nodo. Solo informa: en el guion protege el 409; en ramificación (autoguardado) prevalece la última escritura.

### Editor de ramificación (la parte más compleja)
Rutas `projects/{project}/branching/*`: `index` es una página Inertia, el resto son endpoints **JSON** (bootstrap/app.php fuerza respuestas de error JSON cuando `wantsJson` para `branching/*`, `script/*`, `analysis/*`, `ai/*` y `locks`). El frontend ([features/branching](resources/js/features/branching)) usa `@xyflow/react` y un `fetch` propio con XSRF (`api.ts`), no `router` de Inertia.

- **El servidor es la fuente de verdad**: cada mutación devuelve el grafo completo (`BranchingGraphResource`, con nodos, opciones, variables y entradas de la Biblia) y el cliente lo reemplaza. `useBranchingGraph` guarda borradores con debounce (texto 800 ms, posiciones 500 ms), en serie.
- **Referencias `{{Título}}`**: escribir `{{Nombre}}` en el texto de un nodo crea/enlaza automáticamente el nodo destino y una `DialogueOption` *administrada* (`source_ref` = título normalizado). `ReferenceParser` es puro (sin BD); `ReferenceSyncService` sincroniza dentro de transacciones con bloqueo del proyecto. Las opciones manuales (`source_ref` null) nunca se tocan en la sincronización.
- **Renombrar** un nodo reescribe `{{Antiguo}}` → `{{Nuevo}}` en todos los textos del proyecto conservando `id`/`node_key`. Los títulos son únicos por proyecto comparando la forma normalizada (minúsculas, espacios colapsados) de `displayTitle()`.
- **Inicio y finales** (HU 18): `dialogue_nodes.is_start` (exclusivo por proyecto: marcar uno desmarca el anterior; sin ninguno se usa el de menor id, `start_marked` lo indica) e `is_ending`. `GraphInspector` (solo lectura) calcula el inicio y los avisos con prioridad `isolated` > `no_incoming` > `unreachable` (BFS desde el inicio por opciones con destino; los ciclos alcanzables no avisan) > `no_outgoing` (no aplica a finales), además de `broken_option`.
- **Variables, condiciones y efectos** (HU 19): `branching_variables` (`key` única por proyecto, `type` bool|number, `initial_value`). En `dialogue_options`, `condition` `{var, op, value}` (`== != > >= < <=`; bool solo `== !=`) y `effects` `[{var, op: set|add|sub, value}]` (bool solo `set`); `consequence` y `required_condition` quedan como notas del autor. `BranchingRequest` valida tipos y que la variable sea del proyecto; `BranchingVariableService` reescribe las opciones al renombrar y bloquea borrar o cambiar el tipo de una variable en uso. `BranchingStateEvaluator` es puro (tests unitarios) y tiene un **espejo JS** en `resources/views/reports/partials/branching-state.blade.php`; `npm run test:parity` comprueba que dan lo mismo.
- **Reproductor** (HU 22/23): `DialoguePlayerView` renderiza `reports/dialogues.blade.php` (HTML autónomo, JS y CSS inline, sin red; textos traducidos desde PHP; escribe `@{{` si un comentario contiene llaves dobles), con pestañas Mapa y Jugar: oculta las opciones cuya condición no se cumple, aplica los efectos una vez por elección, muestra las variables y los finales, y Reiniciar vuelve a los valores iniciales. Es la descarga de Reportes y también "Probar recorrido" del editor (`GET branching/playtest[?node=]`, en un iframe, sin escribir en BD).
- **Nodos ↔ Biblia** (HU 20): pivote `dialogue_node_lore_entry` (solo entradas del mismo proyecto), elegida con `LinkPicker` en `NodeEditorPanel`; el contexto del nodo muestra solo la Biblia vinculada.
- `BranchingNodeService` orquesta crear/actualizar/borrar nodos y opciones sobre los servicios anteriores. Existe además un CRUD clásico de diálogos (`DialogueNodeController`, formularios Inertia) que gestiona opciones por su cuenta y conserva `condition`/`effects`.

### IA emocional (Groq) y servicios de análisis
Documentación completa del modelo (pipeline, centroides, prompt, esquema, decisiones) en [docs/modelo-asistencia-emocional.md](docs/modelo-asistencia-emocional.md).
- **Regla de oro:** la IA solo se llama cuando el usuario pulsa un botón (Analizar emociones, Reanalizar, Refinar con IA, Borrador con IA, Revisar consecuencias, Detectar disonancias). Nunca desde `ProjectController@show`, al guardar, ni con observers/eventos. Propone; nunca modifica el guion, el grafo ni guarda fichas sin confirmación.
- **Contrato** `App\Contracts\EmotionAnalyzer` (`analyzeScene(Scene)` → `SceneEmotionResult`, `source()`), elegido en `AppServiceProvider` por `config('gamerdust.ai.driver')`: `GroqEmotionAnalyzer` (si hay `GROQ_API_KEY`) o `KeywordEmotionAnalyzer` (adapta el `EmotionalAnalysisService` simulado, sin red). El contrato permite sustituirlo por un motor externo (ver [docs/narrative-engine.md](docs/narrative-engine.md)).
- **`GroqClient`** (`app/Services/Ai`): `chat/completions` con `json_schema` strict, `reasoning_effort: low`, `include_reasoning: false`. Ante 429/5xx/timeout/JSON inválido reintenta una vez con el modelo de respaldo; si vuelve a fallar lanza `AiUnavailableException`. Cada llamada con proyecto queda en `ai_generations` (`status` ok|fallback|degraded|error, tokens, `latency_ms`, `input_hash`; nunca la clave). La respuesta siempre se valida en PHP (`SceneResultValidator` o el `validate()` de cada servicio).
- **Análisis de escena** (`SceneEmotionService`): caché por `content_hash` (`SceneContextBuilder::contentHash`: guion, vínculos, `updated_at` de fichas y reglas, esencia, locale; "Reanalizar" la ignora; un análisis degradado no se reutiliza) → analizador → `EmotionChangeDetector` → guarda `emotional_analyses` (`source`, `result` completo, `degraded`, `scene_version_id`) y sustituye las filas de `character_emotional_states` de la escena. Si Groq falla con ambos modelos se degrada a palabras clave (`degraded: true`); la edición nunca se bloquea.
- **Análisis de nodo** (HU 45, `NodeEmotionService`): `GET branching/nodes/{node}/analysis` y `POST .../analyze` (respuesta aparte del grafo). Reutiliza el prompt y el esquema de escena con el contexto del nodo (hablante, escena, Biblia vinculada, hasta 3 nodos previos y sus opciones), caché por hash, degradación a palabras clave y `emotional_analyses` polimórfica; tipo `node_analysis`. Se muestra en `NodeAnalysisSection`.
- **Revisiones** (`app/Services/Assist`, sin degradación: 503 con mensaje amable): `ConsequenceReviewService` (HU 50, `POST ai/consequence-review`, tipo `consequence_review`: incompatibilidades por `option_id`, convergencias como revisión, condiciones imposibles y efectos sin uso; máx. 40 nodos) y `LudonarrativeReviewService` (HU 56, `POST ai/ludonarrative-review`, tipo `ludonarrative_review`: cada mecánica frente a sus escenas, personajes y reglas vinculadas; sin vínculos → "Contexto insuficiente" sin llamar a la IA). Los ids que la IA inventa se descartan.
- **Contexto** (`SceneContextBuilder`): esencia del proyecto (incluido el encargo), lugar (`location_id`) y sus reglas (`lore_entry_links`), personajes de `character_scene` (con valores y conflicto interno) y sus reglas (`character_lore_entry`), máx. `gamerdust.ai.max_context_items`, texto de `ScenePlainText` (conserva quién habla) recortado a `max_scene_words`. **Estado previo** de un personaje: su estado en la escena anterior analizada más cercana (por `order`) → si no, su estado inicial del autor (`characters.initial_emotion/initial_intensity` + `EmotionTranslator::fromAuthor`) → si no, ninguno.
- **"VAD invisible":** internamente v/a/d en 0-1; en la interfaz y en los reportes solo Tono/Tensión/Control del personaje y la emoción (`EmotionTranslator`, clase pura). Umbrales, centroides, colores, intensidades y umbral de cambio abrupto viven **solo** en `config/gamerdust.php`; el frontend los recibe por la prop `emotionCatalog` (sin números en TS). El modo técnico (localStorage) muestra los valores crudos. Las filas antiguas de `emotional_analyses` sin `content_hash` son de la simulación (valencia -1..1) y no se mezclan.
- **Regla vs. IA:** `EmotionChangeDetector` decide (cambio abrupto si `max(|Δv|,|Δa|,|Δd|) > 0.40`); la IA solo explica (`change_justified`). Rojo = abrupto y no justificado; ámbar = abrupto y justificado. También a nivel de escena frente a la escena anterior analizada.
- **Generar y refinar** (`app/Services/Assist`): `CharacterDraftService` (borrador que rellena la ficha nueva vía `useEntryEditor().fillNew`, sin guardar) y `BlockRefineService` (propuesta para un bloque; "Aplicar" solo toca el borrador local y entra en deshacer/rehacer). Valoraciones 👍/👎 en `ai_feedback` (`emotional_analysis_id` + `item_index` o `ai_generation_id`).
- **Límite propio:** `RateLimiter` `ai` (10/min por usuario) en las rutas que llaman a la IA (se aplica antes de la autorización: un 429 puede llegar antes que un 403).
- **Validaciones por regla** (`NarrativeValidationService`, se ejecuta en `ProjectController@show`, Análisis IA y el reporte): reglas de la Biblia y **límites de producción** de `project_constraints` (`max_characters`, `max_pages` estimadas con `ProductionUsage` = palabras del guion / `gamerdust.validation.words_per_page` (250), `max_budget` frente a la suma de puntos de `NarrativeCostEstimatorService`; igualar no es exceso, sin límite no hay alerta) y `requires_twist` como revisión (`severity` review). Cada alerta tiene `status` pending|resolved|dismissed, `subject` (morph al elemento afectado, con enlace en `toPayload()`) y `fingerprint` (tipo + elemento + causa): una alerta cerrada no se recrea mientras la causa no cambie; las pendientes sin causa se borran. `PATCH validations/{validation}` cambia el estado. `NarrativeCostEstimatorService` (heurística de coste al crear/editar) sigue siendo simulado, igual que el último análisis que muestra el Panel del proyecto (`EmotionalAnalysisPanel`).

### Observabilidad
Canal de log `gamerdust` (`config/logging.php`, diario en `storage/logs/gamerdust-AAAA-MM-DD.log`), escrito solo por `App\Support\OpsLog`, que admite una lista cerrada de claves (ids, códigos, tiempos; nunca la clave, el prompt, la respuesta, el texto narrativo ni el mensaje de una excepción). Eventos: `ai.attempt_failed`, `ai.fallback`, `ai.unavailable`, `ai.degraded` (desde `GroqClient`), `ai.invalid_output` (`AiAssistController`) y `http.server_error` (middleware global `LogServerErrors` para cualquier 5xx). Tabla de eventos y pasos de producción en [docs/despliegue.md](docs/despliegue.md).

### Esquema
Tablas de dominio en `2026_06_04_000000_create_gamerdust_tables.php` más migraciones incrementales posteriores: idioma/favorito, campos de setup narrativo, `expected_outcome` en restricciones, campos de ramificación (`title`, `node_key`, `pos_x/pos_y`, `source_ref`); IA emocional (columnas de seguimiento en `ai_generations`, columnas de IA en `emotional_analyses`, `character_emotional_states`, `characters.initial_emotion/initial_intensity`, `ai_feedback`); cierre del MVP: `project_constraints.assignment/max_characters/max_pages/max_budget/requires_twist`, `characters.values/inner_conflict`, `narrative_validations.status/subject/fingerprint` (sustituye a `resolved`), `dialogue_nodes.is_start/is_ending`, `branching_variables`, `dialogue_options.condition/effects`, `dialogue_node_lore_entry`, `project_members` y `edit_locks`. `project_constraints` es 1:1 con proyecto (store y update usan el mismo método `store`).

## Convenciones
- `.editorconfig`: 4 espacios, LF (YAML 2 espacios).
- Validación en FormRequests (`app/Http/Requests`, los de ramificación heredan de `Branching/BranchingRequest`; los de acceso en `Requests/Auth`).
- Tests de feature con `RefreshDatabase`; los proyectos se crean vía `$user->projects()->create([...])` (solo existe `UserFactory`); los miembros con `$project->members()->create(['user_id' => ..., 'role' => ...])`.
- Los métodos de test se nombran en español (`test_crea_el_proyecto_...`): Collision usa el nombre como descripción en consola. Los tests de JS están en `tests/js/` (Node 24 ejecuta TypeScript nativo).
- `CumbreMudaSeeder` (lo llama `DatabaseSeeder`) crea un proyecto de demostración completo para `test@example.com` (contraseña `password`): guion, Biblia, mecánicas, un grafo con inicio y tres finales declarados, variables (`confianza_cordada`, `confianza_lucia`, `cabo_escondido`) con condiciones y efectos, y un equipo de ejemplo (`editora@example.com` editor y `lector@example.com` lector, misma contraseña). Sus análisis emocionales están redactados en `CumbreMudaAnalyses` (sin red). Nunca se ejecuta en producción.
